# 生图请求异常排查记录

本文记录本地生图测试中出现的两类独立问题、排查证据及当前处理情况。外部服务仅按用途描述，不记录生产业务域名、API Key 或完整图片链接。

## 1. 图片已生成，前端仍在等待

### 现象与证据

- 用户反馈一次生成四张图片，其中两张在后端完成后，前端仍持续转圈；接口已返回图片 URL。
- 用户在新标签页可以流畅打开图片链接。
- Chrome Network 截图显示，异常图片请求由 `web/src/services/image-storage.ts` 的 `fetchImageBlob()` 发起，状态为 `canceled`，耗时约 10 分钟，传输量为 0.0 KB。
- Timing 中约 10 分钟消耗在 `Initial connection` 阶段。
- 此前命令行排查同类图片链接时，既观察到数秒完成下载，也观察到收到 HTTP 200 后传输长时间停滞；曾收到 `Access-Control-Allow-Origin: *`。这些是不同请求的观察，不能视为浏览器异常请求的响应证据。
- 用户随后使用同一个上游再次测试，暂未复现；用户确认该上游返回图片 URL，而非 Base64。

### 代码流程

```text
生图接口返回图片 URL
  → uploadImage()
  → fetchImageBlob() 获取图片
  → 解码图片并写入浏览器 IndexedDB
  → 生成预览图
  → 更新任务成功状态
```

对应源码：

- `web/src/services/api/image.ts`：解析生图接口结果。
- `web/src/services/image-storage.ts`：获取图片、解码和本地保存。
- `web/src/pages/image/generation.ts`：等待图片处理结束后更新任务状态。

图片下载已有 10 分钟超时，到时会取消请求。截图中的耗时与该逻辑吻合。该请求卡在连接阶段，尚无证据表明本次等待由 IndexedDB、图片解码或缩略图处理引起。界面将获取图片的时间也显示为生成中，导致用户感觉后端完成后仍在生成。

### 当前结论与决定

现有证据倾向于图片服务、CDN 或浏览器到图片服务的网络连接偶发异常，尚未确认具体根因。新标签页成功、后续重测成功，均不能证明此前那次连接正常，也不能单独确定故障属于哪一端。

曾考虑过返回格式发生变化，但缺少旧响应证据，不能把“以前返回 Base64、现在返回 URL”写成事实。同一上游也不保证每次图片域名、分发节点及连接条件相同。

按用户决定，暂不修改图片下载、超时或重试行为，也不将此问题标记为已修复。

讨论过但尚未实施的措施：保存原始图片 URL、区分生成与获取图片状态、提供仅重新获取图片的操作、补充阶段错误信息，以及下载失败后的远程图片展示。远程展示同样依赖链接可访问，不能保证一定成功；有限自动重试的参数尚未确定。

## 2. Gemini 生图请求被跨域预检拦截

### 现象与证据

- 本地页面来源为 `http://127.0.0.1:3000`。
- Gemini 原生请求直接访问远程后端的 `/v1beta/models/gemini-3-pro-image-preview:generateContent`。
- Network 显示 OPTIONS 返回 204，但对应请求显示 `CORS error`。
- Console 明确提示预检响应缺少 `Access-Control-Allow-Origin`。
- 随后发送不带密钥的 OPTIONS 请求核对：当次响应确实没有 `Access-Control-Allow-Origin`，`Access-Control-Allow-Headers` 中也未包含 Gemini 使用的 `x-goog-api-key`。

HTTP 204 只代表 OPTIONS 返回了响应，浏览器仍需验证允许来源、方法及请求头。此次错误发生在调用生图接口之前，与第一类图片下载连接超时不同。

### 原因与本地修复

OpenAI 格式请求使用现有的 `resolveApiBaseUrl()`，在开发环境把默认后端地址转换为 `/panlai-api/`；Gemini 的 `geminiBaseUrl()` 原先直接拼接远程地址，漏用了该转换。

本次仅调整 `web/src/services/api/image.ts` 的导入及基础地址处理，让 Gemini 共用现有地址转换函数，继续使用原有 Vite 开发代理。默认后端的本地请求路径变为：

```text
http://127.0.0.1:3000/panlai-api/v1beta/models/模型名:generateContent
```

保留既有 `/v1`、`/v1beta` 后缀规则、请求体、鉴权头和超时设置；其他自定义后端沿用现有地址规则。共用该函数的内置 Gemini 生图、编辑、模型列表及文本流式请求均会使用转换后的地址。

### 验证状态与适用范围

- 已通过本地 `/panlai-api/v1beta/models` 发出不带密钥的请求，收到后端 `401 UNAUTHENTICATED`、`API key is required`，证明本地代理路径可到达后端。
- 该连通性检查没有调用生图接口；修复后用户已确认本地 Gemini 生图测试通过。编辑、模型列表、文本流式请求等共用入口尚未单独确认验收。
- 按项目约定未执行编译、构建或语法检查。
- 此修复解决默认后端的本地开发请求路径；正式部署未配置同源代理时，仍需后端正确处理 OPTIONS 和实际响应的 CORS。
- 后续本地代理 GET 响应中观察到允许 `x-goog-api-key` 的响应头，但 GET 的响应不能代替先前失败的 OPTIONS 预检结果，不能据此宣告后端 CORS 已修复。

## 3. 再次复现时收集的信息

优先检查失败的是生图接口，还是接口返回后的图片下载请求，并保留以下信息：

1. 模型名称、调用格式、请求域名和路径；完整签名 URL 仅私下留存。
2. Network 的状态、类型、Initiator、耗时及 Timing。
3. Console 的完整错误文本。
4. 若为跨域：OPTIONS 的请求来源、请求方法、请求头名称，以及响应中对应的允许项。
5. 若为图片下载：返回格式、图片域名、传输量及新标签页访问结果，分别记录每次请求。

提供截图或日志前移除 API Key、Authorization、Cookie 和图片签名参数。未获授权时不要为排查重复调用可能计费的生图接口。

## 4. 尚未确定的其他报错

用户曾反馈首次生成出现与 1K 或 1024×1024 有关的尺寸限制提示，但缺少完整错误及对应请求参数。当前不能把该提示与上述两类问题归为同一原因，也没有针对它修改尺寸逻辑。
